# Native boundary checks

The bounded CPU operation accepts tensors from code already running in its process. It is not a sandbox for untrusted Python, models or native libraries. Malformed-argument rejection and memory diagnostics provide robustness evidence. They do not by themselves establish a remotely exploitable vulnerability or a secure service. This distinction agrees with [PyTorch's security policy](https://github.com/pytorch/pytorch/blob/9544ec5e23cef8a0a4ac3f44c27e0e94d651ad02/SECURITY.md).

## A combined view-state bug

The v0.1.0 installed Windows package admitted a stepped, noncontiguous forward input when that tensor also carried a logical negative bit. This was reproduced separately for values, logits and offsets. The ordinary noncontiguous case and contiguous negative case were already covered. Their combination was missing.

PyTorch's [v2.9.1 Negative fallback](https://github.com/pytorch/pytorch/blob/v2.9.1/aten/src/ATen/native/MathBitsFallback.h) can clone a negative view before CPU redispatch. A stepped slice can become contiguous during that clone. The CPU kernel therefore saw an admitted layout after the original unsupported layout had disappeared.

The repair registers Negative-key handlers for both native operations. They validate original metadata before resolving negative views, then delegate to the existing CPU implementation. This keeps contiguous negative inputs and strided upstream gradients useful while protecting direct dispatcher entrypoints as well as the public function. It does not widen the forward contract or introduce another custom operation.

## Generated checks and mathematical properties

`tests/generated_cases.py` contains the deterministic case engine shared by pytest and the bounded campaign. It compares valid native output, autograd and direct private-backward results with independently differentiated reference composition. Malformed admission cases exercise both native operations, including extreme offsets and combined view states. Inputs are bounded before allocation. Category counters describe the cases executed, not branch or edge coverage.

A useful example is a consistent within-group permutation. Reordering both values and their logits preserves the weighted sum. The corresponding input gradients follow the same permutation. A logit shift is valid only when the shifted input remains within the finite numerical range. Uniform logits provide an independent mean-pooling check. These relations supplement reference comparisons and finite differences.

Consensus helped locate Segura et al.'s [survey on metamorphic testing](https://eprints.whiterose.ac.uk/id/eprint/110335/1/segura16-tse.pdf). Its discussion of relation preconditions and approximate numerical comparisons informs this test design. It supplies no measured fault-detection result for ragged-pool.

A wider uninstrumented seed sweep exposed a useful test-oracle problem at seed 184. The float32 PyTorch reference's score gradient differed from native by 3.14e-6 near cancellation, which exceeded the original absolute tolerance. Against the same reference composition run in float64 on the exact float32 inputs, native differed by at most 4.57e-8. Generated float32 gradient checks now use that higher precision derivative cast to float32; the float32 reference still checks forward output. This is a numerical test correction, not a tolerance increase or evidence of a native defect.

## Generated second-order qualification

`tests/generated_second_order_cases.py` extends the generated checks to the accepted packed and padded eager second derivatives. It exercises both registered public autograd and direct private second backward against independently differentiated per-group PyTorch math. All three derivative outputs are compared, including the derivative with respect to the first upstream gradient `g`. This adds combinations to the existing fixed second-order checks without changing the native formula, API or compiler scope.

Fixed pytest seeds establish the declared categories in both dtypes. They cover empty/singleton/mixed groups, padded holes, bounded endpoints, unused first-gradient branches and ordinary upstream views. Within-group permutations move values, logits and their adjoints together. Safe logit shifts preserve admission, and equivalent padded layouts retain the same selected items and adjoints. Those relations supplement the independent oracle. Category counters record checks that passed, not branch or edge coverage.

Float32 comparisons use the independent composition differentiated in float64 and cast back to the public dtype, preserving cancellation evidence. Small float64 interior fixtures use central directional differences of the first-gradient scalar, including perturbations of `g`. Numerical differences use nonoverlapping storage, with view handling tested separately. This follows the distinction between mathematical checks and registration checks in the [PyTorch testing API](https://docs.pytorch.org/docs/2.9/library.html#torch.library.opcheck) and the [second-gradient mechanics](https://docs.pytorch.org/docs/2.9/notes/gradcheck.html#gradgradcheck-implementation).

An explicit sensitivity control drops only `dg` from a local test candidate and requires the same comparator to reject it for that output. A two-item witness has `dg=-2` even at `g=0`. The control does not alter installed registrations and is not a discovered production defect. It demonstrates sensitivity to this particular omitted derivative, rather than proving complete fault detection. Input values, versions, strides and logical-negative state remain part of the checks. Ignored nonfinite padding is selected out before arithmetic.

The case module is shared with a separate bounded ASan campaign through the existing runner's `--cases` interface. PRs request 30 seconds plus a five-second prefix replay. Main and manual runs request five seconds plus the replay. The original first-order ten-minute PR campaign, main smoke and replay remain unchanged. Both new receipts must identify the expected case-file bytes, loaded native library and source revision, complete positive iterations and record positive core second-order counters. Fixed pytest cases establish categories independently of how many timed iterations finish.

`second-order-campaign.json`, `second-order-replay.json` and their in-flight seed files are retained in the existing evidence artifact, including on failure. A same-seed short replay repeats a deterministic prefix, not every case from the longer campaign. A running, interrupted or empty receipt is not acceptance. The test modules are included in the checked source distribution. The instrumented campaign uses the runner copied from the Git checkout; that runner is not part of the source distribution, so the archive alone does not reproduce the sanitizer workflow.

These are bounded qualification checks. They establish neither memory safety nor a security certification, model-quality result or new derivative capability. An actual completed workflow and revision establish execution. The older failures and successful run below retain their original scope.

## Instrumented execution

The [native ASan workflow](../.github/workflows/native-asan.yml) selects Ubuntu 24.04 x86-64, CPython 3.11.8, PyTorch 2.9.1+cpu, GNU C++ 13 and C++17. The actual compiler and runner image belong to each run's log. It builds the same production extension with `RAGGED_POOL_ASAN=1`, using `-O1 -g -fno-omit-frame-pointer -fsanitize=address` and an ASan link flag. The matching shared runtime is resolved through that compiler and preloaded before Python starts. Ordinary wheels remain separate and uninstrumented.

The [first Linux PR run](https://github.com/T92T1914/ragged-pool/actions/runs/39384343118) used Clang 18. Its instrumented wheel built and its injected control reported the expected heap error, but the production extension could not load because a `TensorBase::const_data_ptr<float>` symbol was unresolved. No production sanitizer result follows from that run. The workflow now selects the runner's existing GNU C++ 13 and matching `libasan` to test another compiler route against the installed PyTorch binary. Only a subsequent executed run can establish whether that route works.

The [first GNU C++ 13 run](https://github.com/T92T1914/ragged-pool/actions/runs/39384861553) also built and passed the injected control. Its production step exited before pytest emitted a test result, and the campaign did not start. This failure was retained without assigning a cause. The next run separated an ASan-preloaded import probe from pytest and left pytest output uncaptured.

The [second GNU C++ 13 run](https://github.com/T92T1914/ragged-pool/actions/runs/39385481168) imported the installed extension and collected 155 tests. On the first expected malformed-input C++ exception, GCC's ASan runtime stopped with `real___cxa_throw == 0`. This is an interceptor setup failure, not a reported out-of-bounds access in the operator. The campaign again did not start. An [accepted libcamera fix for the same failure](https://patchwork.libcamera.org/patch/21811/) explains that dynamically loading a C++ module from Python can leave ASan without its C++ standard-library dependency when linked with `--as-needed`. This workflow now preloads the compiler-resolved `libstdc++.so.6` after `libasan.so`. A separate throw-and-catch control must also pass before production tests start. A later executed run must establish whether this resolves the issue here.

The later [main run at 9866e00e](https://github.com/T92T1914/ragged-pool/actions/runs/39488914470) completed the runtime controls, installed production tests and bounded campaign successfully. That executed result qualifies this revision and instrumented environment. The earlier failed runs above remain part of the record.

The job installs its instrumented wheel outside the checkout. It first qualifies the runtime/shared-library loading route with a C++ exception probe and a disposable injected heap error, requiring the expected ASan diagnostic and a nonzero exit for the latter. These controls are not discovered project defects. The production campaign separately checks the loaded extension path, SHA256, dispatcher load identity, ASan symbols and runtime activation. It executes the existing tests, generated cases and both installed training consumers.

First-order PR runs request a ten-minute single-worker campaign followed by a five-second replay. Main-branch and manually dispatched runs use a five-second campaign and replay. The separate second-order stage uses the shorter bounds described above. Seeds begin at 20261020. Tensor and case bounds are fixed in each case engine. The process uses one PyTorch thread, at most two build jobs, a four-GiB sampled RSS budget and a finite job timeout. RSS is checked between bounded cases, not enforced as a hard OS memory cap. An in-flight seed file and checkpointed JSON preserve the active case if native code terminates Python. A running or interrupted receipt is not a pass.

Instrumentation covers this extension's compiled native code. Python and the prebuilt PyTorch dependency are not rebuilt with ASan. Leak detection is disabled explicitly. This is an AddressSanitizer campaign, not general undefined-behavior checking, coverage-guided fuzzing, an edge-coverage measurement or proof of memory safety. No suppressions or relaxed runtime-order checks are used. [GCC 13 AddressSanitizer options](https://gcc.gnu.org/onlinedocs/gcc-13.3.0/gcc/Instrumentation-Options.html).

The actual run and revision determine execution status. Workflow source is not a successful campaign. The installed Windows release-wheel checks remain separate from this Linux instrumentation configuration. No Linux distribution or cross-version ABI promise follows from it. The local MSVC 14.44 installation had x86 ASan components but no discovered x64 runtime, so local Windows sanitizer execution was not claimed.
